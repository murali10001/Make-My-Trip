1. Executive Summary & Recent Enhancements

MakeMyTour is an enterprise-scale, cloud-native travel booking and hospitality management web platform inspired by industry aggregators such as MakeMyTrip. The platform is designed to handle key distributed systems challenges:

Core Distributed Systems Capabilities:
  1. High-Concurrency Seat & Room Selection: Synchronized critical section mutexes preventing double-booking across 72 aircraft seats and hotel room tiers with HTTP 409 Conflict mapping.
  2. Multi-Factor Dynamic Pricing Engine: Mathematical surge formulas factoring inventory depletion (+15%), calendar seasonality (+20%), and departure urgency decay, paired with 24-hour cryptographic fare locks.
  3. Dual-Channel Real-Time Push Mesh: Unidirectional sub-second telemetry via 8 Server-Sent Events (SSE) hubs, combined with persistent HTML5 Web Push Notifications backed by Service Workers and VAPID keys.
  4. Deterministic Cancellation & Asynchronous Refund FSM: Piecewise time-decay policy engine (90%, 75%, 50%) decoupled into a non-blocking 3-step background daemon Finite State Machine.
  5. Authoritative Payment Provider Gateway Ledger: Dedicated payment capture and refund ledger (PaymentProviderService) verifying charges and generating official Acquirer Reference Numbers (ARN).
  6. Polymorphic UGC Reviews & Lexicon Sentiment NLP: In-memory weighted dictionary (+2.0 to -2.0) with intensifiers/negators, 4-aspect sub-ratings, and role-based access control (RBAC) quarantine moderation.
  7. Explainable AI (XAI) Recommendation Engine: Centroid destination clustering with transparent reasoning vectors and closed-loop feedback affinity learning.

1.1 Recent Engineering Enhancements Audited

The codebase has recently incorporated major production-readiness enhancements:

  • Web Push Notifications (VAPID): Integrated browser Service Worker (makemytour/public/sw.js) with VAPID key pairs. Browser push subscriptions are persisted in MongoDB (push_subscriptions) and notified simultaneously alongside SSE.
  • Payment Provider Gateway Ledger (PaymentProviderService.java): Establishes verified transactions, validates captured payments prior to cancellation, and issues official banking Acquirer Reference Numbers (e.g. ARN-700109283912).
  • Role-Based Security for Moderation: Enforced Spring Security filter chain with .hasAnyRole("ADMIN", "MODERATOR") and controller-level token/header inspection (isAuthorizedModerator) returning HTTP 403 Forbidden upon unauthorized access.
  • Hotel Room Reservation Endpoints: Introduced POST /api/selection/reserve-room and /release-room enabling atomic hotel inventory holds matching the aircraft seat locking pipeline.
  • 14-Day Historical Volatility Matrix: Automated recording of genuine price history records (PriceHistory in price_histories) with day labels and volatility trends.

3.1 Core Architecture Principles

Document Aggregate Modeling
Customer bookings are stored as embedded documents directly inside the users collection. This eliminates multi-table relational SQL JOINs during dashboard queries and guarantees atomic updates during ticket issuance and cancellations.
Push-Over-Pull Telemetry
Traditional browser HTTP polling is replaced with Server-Sent Events (SSE). Background workers run delta-state evaluations every 5 seconds, pushing only modified entities to clients, which eliminates broadcast storms and DOM thrashing.

4. The 6 Core Features & Domain Workflows

Workflow 1: Real-Time Flight Telemetry & Radar Pipeline

Problem Solved: Eliminates server thrashing from client polling while delivering sub-second delay alerts.

  • Startup Seeding: FlightStatusService.java:50-59 synchronizes catalog flights into live status records using Indian Standard Time (Asia/Kolkata).
  • Delta-State Daemon: Every 5,000ms, FlightStatusScheduler.java calls validateAndSyncChangedFlights(). Only flights whose status or delay changed are saved and pushed via SSE.
  • Multi-Flight Watchlist: Batch tracking endpoint POST /api/flight-status/tracked accepts multiple flight numbers and returns consolidated delay metrics in a single network round-trip.

Workflow 2: Multi-Factor Dynamic Pricing Engine & 24h Fare Freeze

Mathematical Surge Algorithm (PricingService.java:103-134): 

P_final = round( P_base * (1 + (delta_demand + delta_season)/100) * M_departure )
  • Inventory Scarcity (delta_demand): Seats ≤ 25 ⇒ +15%; 26–70 ⇒ +5%; >70 ⇒ 0%.
  • Seasonality Factor (delta_season): Holiday Peak ⇒ +20%; Weekend ⇒ +10%; Regular ⇒ 0%.
  • Departure Multiplier (M_departure): <24h ⇒ 1.25x; 24–72h ⇒ 1.15x; 72–168h ⇒ 1.05x; >168h ⇒ 1.00x.
  • 24-Hour Fare Freeze Lock: freezePrice() generates a cryptographic session token FRZ-XXXX with expiresAt = now + 24 hours. If expired at checkout, PriceFreezeExpiredException is thrown and mapped to HTTP 410 Gone.
  • 14-Day Historical Tracking: recordGenuinePriceHistory(...) logs daily points into price_histories.

Workflow 3: Cancellation Engine & Asynchronous Refund FSM

Time-Decay Refund Algorithm (RefundService.java:86-98): 

Refund Percentage =
  90%  if delta_t > 72 hours (Flexible Advance Policy)
  75%  if 24h <= delta_t <= 72 hours (Standard Policy)
  50%  if delta_t < 24 hours (Last-Minute Policy)
  • Predefined Cancellation Reasons: Validates against PREDEFINED_REASONS list (e.g. "Medical emergency", "Flight delay"); throws IllegalArgumentException (HTTP 400) if invalid.
  • Payment Provider Verification: Calls PaymentProviderService.verifyCapturedPayment(...) to authenticate the charge.
  • Instant Inventory Restoration: Booking is marked CANCELLED, flight seats or hotel room inventory are incremented, and the reserved seat is released back to AVAILABLE.
  • Asynchronous 3-Step FSM: HTTP cancellation returns in <40ms with status REQUESTED. The background daemon (RefundStatusScheduler.java, running every 2000ms) transitions: 
    REQUESTED (Step 1, <40ms) ──[3s]──> APPROVED (Step 2) ──[4s]──> PROCESSING (Acquirer ARN) ──[5s]──> COMPLETED (Verified Credit)

Workflow 4: Aircraft Seat & Hotel Room Selection Concurrency

  • Aircraft Cabin Layout: 72 seats in 12 rows across standard Airbus A320 3-3 configuration (A, B, C aisle D, E, F).
  • Concurrency Mutex: reserveSeat(...) in SelectionService.java:216 is declared synchronized. If a thread finds a seat already marked OCCUPIED, it throws SeatUnavailableException, mapped by SelectionExceptionHandler.java to HTTP 409 Conflict.
  • Hotel Room Reservation: reserveRoomOption(...) in SelectionService.java atomically decrements availableRooms; throws InsufficientCapacityException (HTTP 400) if sold out.
  • Real-Time Broadcast: On successful claim, an SSE event is pushed to all viewers, disabling the seat button instantly on other screens.

Workflow 5: Polymorphic Reviews, Sentiment NLP & RBAC Moderation

  • Aspect Lexicon (ReviewSentimentAnalyzer.java): In-memory dictionary with pre-compiled valence scores (+2.0 exceptional, -2.0 filthy), intensifiers (1.5x), and negators (-1.0x).
  • Aspect Dimensions: Generates 4 discrete sub-ratings: Cleanliness, Service, Location, and Value.
  • Verified Booking Gate: Users cannot review unless they hold a completed booking; throws UnverifiedReviewException (HTTP 403 Forbidden).
  • Administrative RBAC: Moderation queue requires ADMIN or MODERATOR role via isAuthorizedModerator; returns HTTP 403 Forbidden upon violation.

Workflow 6: Hybrid Recommendation Engine & Explainable AI (XAI)

  • Multi-Factor Additive Model: Destination clustering blended with user booking history (+8 pts), preference alignment (+4 pts), and community feedback. Clamped between 70% and 99%.
  • Transparent XAI: Generates human-readable reason tooltips explaining why a destination was picked.
  • Cold-Start Heuristic: New users receive curated top-rated properties from each centroid.

5.1 Dual Real-Time Push Mechanism (SSE + Web Push)

How Notifications Are Broadcast to Users:
When NotificationService.createNotification(...) is called:
  1. In-Memory SSE Dispatch: broadcastRealTimeNotification(...) iterates active SseEmitter instances in userEmitters.get(userId), pushing the event instantly over the active HTTP connection.
  2. Persistent Web Push Dispatch: dispatchWebPushToSubscribers(...) queries active browser push subscriptions in MongoDB, encrypts the payload using the server's VAPID private key, and dispatches it to browser push endpoints, waking up public/sw.js even if the browser tab is closed!
  3. Heartbeat Maintenance: Every 25,000ms, schedulers transmit comment pings (:keep-alive) to prevent cloud routers from terminating idle connections.

7. Cloud Deployment Topology: Render vs. Vercel

MakeMyTour is deployed on Render Cloud Platform, not Vercel. In technical interviews, this is a major architectural talking point demonstrating deep distributed systems knowledge:

Architectural Requirement Vercel Serverless Functions Render Web Service (Docker Container)
Process Lifecycle Ephemeral: Terminated immediately after HTTP response Continuous: 24/7 Always-On Container Process
Execution Timeout Hard cutoff: 10–15 seconds maximum No Timeout: Persistent TCP connections remain active
Server-Sent Events (SSE) DROPS: Connections killed after 10–15 seconds NATIVE: Streams stay open indefinitely
Background Daemons (@Scheduled) BROKEN: Daemon threads killed when function sleeps OPERATIONAL: Schedulers run every 2s & 5s reliably
JVM Cold Starts 15–25 second latency penalty per cold invocation ZERO: JVM is pre-warmed in container memory
Database Connection Pooling Rapid container churn exhausts MongoDB Atlas pool STABLE: Persistent HikariCP connection pool
Concurrency Mutex Locks Ineffective across stateless lambda invocations GUARANTEED: Serialized locking within JVM

11.3 Top 12 Technical Interview Questions & Word-for-Word Model Answers

Q1 How did you design exception handling and what HTTP status codes did you choose?
Model Answer: We designed an Ordered Multi-Tier Exception Handler architecture using Spring's @RestControllerAdvice. To prevent generic internal leaks, 10 domain-specific advisors are configured with @Order(Ordered.HIGHEST_PRECEDENCE), mapping domain exceptions to strict RFC status codes:
  • 400 Bad Request: Validation failures (BookingFailedException, InsufficientCapacityException, CancellationNotAllowedException, InvalidCouponException, InvalidReviewException).
  • 401 Unauthorized: Authentication failures (InvalidCredentialsException).
  • 403 Forbidden: Authorization failures (UnverifiedReviewException for guests reviewing unbooked stays, and non-admin attempts to access moderation).
  • 404 Not Found: Non-existent entities (FlightNotFoundException, HotelNotFoundException, UserNotFoundException, RefundNotFoundException, PriceFreezeNotFoundException).
  • 409 Conflict: State race conditions (SeatUnavailableException when 2 users race for a seat, EmailAlreadyExistsException).
  • 410 Gone: Expired temporal tokens (PriceFreezeExpiredException when 24h expires).
  • 503 Service Unavailable: DataAccessException during MongoDB disconnects (with graceful empty array fallbacks for catalog listings).
All handlers return a standardized ApiErrorResponse JSON payload containing status, error, message, path, and ISO timestamp.
Q2 How do you prevent double-booking when 50 concurrent travelers click the exact same flight seat simultaneously?
Model Answer: In SelectionService.java, the reserveSeat method is declared synchronized. In our single-instance container deployment on Render, this establishes an intrinsic JVM monitor lock that serializes concurrent worker threads attempting to claim seats. When multiple requests target the same seat simultaneously, the first thread checks MongoDB, verifies that the seat is not OCCUPIED, marks it OCCUPIED, saves it, and broadcasts an SSE update. Subsequent contending threads enter the synchronized block, discover that the seat is already OCCUPIED, and immediately throw SeatUnavailableException. Our SelectionExceptionHandler.java intercepts this exception and returns an HTTP 409 Conflict response. Connected clients immediately receive the SSE seat update, disabling that seat on all screens in real time.
Q3 Why did you choose Server-Sent Events (SSE) over WebSockets or Polling?
Model Answer: Telemetry, price updates, and refund state progressions are fundamentally unidirectional server-to-client push streams. WebSockets are bidirectional and protocol-heavy: they require protocol upgrading, custom ping/pong frame management, stateful socket servers, and higher memory overhead per connection. Short polling floods the server and database with redundant queries, while long polling incurs frequent HTTP reconnection churn. SSE operates over standard HTTP/1.1 or HTTP/2, natively supports browser auto-reconnection with exponential backoff, traverses corporate firewalls seamlessly, and in Spring Boot requires only lightweight SseEmitter instances managed in thread-safe CopyOnWriteArrayList registries.
Q4 Walk me through your asynchronous refund architecture and Payment Gateway integration.
Model Answer: Processing banking refunds synchronously in the user request thread is an architectural anti-pattern: payment gateways suffer from network jitter, bank APIs require retries, and holding open HTTP request threads leads to thread pool starvation. In RefundService.java, when a cancellation arrives, we validate the cancellation reason against predefined rules, verify the captured payment via PaymentProviderService, calculate the refund amount using our piecewise time-decay formula (90%, 75%, or 50%), restore flight seat or hotel room inventory immediately via restoreInventory(), persist a RefundRequest in status REQUESTED, and return HTTP 200 within 40ms. Our background daemon RefundStatusScheduler.java runs every 2000ms using @Scheduled(fixedRate = 2000), polling active refunds and advancing them through deterministic lifecycle stages (REQUESTED → APPROVED → PROCESSING → COMPLETED) using elapsed time gates (3s, 4s, 5s), issuing verified Acquirer Reference Numbers (ARN) and Gateway Refund IDs while dispatching live SSE events to the user's browser.
Q5 How does your dynamic pricing algorithm compute surges, and how is the price freeze token verified?
Model Answer: Dynamic pricing is calculated in PricingService.java using: P_final = round(P_base * (1 + (delta_demand + delta_season)/100) * M_departure). Scarcity surge adds +15% when seats drop to 25 or below, and +5% when seats are between 26 and 70. Seasonality adds +20% during peak holiday periods and +10% on weekends. Departure proximity multiplier scales exponentially up to 1.25x inside 24 hours. To protect travelers from sudden spikes during booking, freezePrice() generates an immutable token (FRZ-XXXXXXXX) stored in MongoDB with an expiresAt timestamp set 24 hours into the future. At checkout, getFreezeStatus() validates whether LocalDateTime.now().isAfter(freeze.getExpiresAt()). If expired, it marks the document active = false, saves it back to the database, and throws PriceFreezeExpiredException, which PricingExceptionHandler.java maps to HTTP 410 Gone.
Q6 Why did you deploy your Spring Boot backend on Render instead of Vercel Serverless?
Model Answer: Vercel Serverless functions are ephemeral lambda instances designed for short stateless request-response lifecycles with hard 10–15 second timeouts. MakeMyTour relies on persistent TCP streams for 8 Server-Sent Events hubs, continuous background @Scheduled daemon workers (running every 2s and 5s for flight status synchronization and refund progression), in-memory concurrency locks, and stable MongoDB connection pools. Serverless lambdas terminate background scheduler threads as soon as the HTTP response finishes, drop SSE connections after 10 seconds, suffer from 15-second JVM cold starts, and exhaust MongoDB connection limits due to constant container churn. By deploying a multi-stage Docker container (eclipse-temurin:17-jre) on Render, the JVM stays warm 24/7, background schedulers run uninterrupted, and real-time streaming works reliably.
Q7 How does your dual real-time notification push system work with Web Push and Service Workers?
Model Answer: We engineered a dual-channel real-time notification push architecture. For active in-app sessions, Spring Boot uses SseEmitter streaming over persistent TCP connections to update top navigation badges and toast alerts in real time. For background or closed-browser alerts, we integrated the W3C Web Push API. The client registers a service worker (/sw.js), retrieves our public VAPID key from GET /api/notifications/vapid-public-key, subscribes via PushManager, and registers the subscription in MongoDB (push_subscriptions). When NotificationService.createNotification(...) is triggered, it broadcasts via SSE to active browser windows and dispatches web push payloads to all registered push endpoints, waking up the service worker to display system tray notifications even if the tab is closed.
Q8 How does your sentiment analysis engine work without heavy machine learning models?
Model Answer: In ReviewSentimentAnalyzer.java, we engineered a high-performance rule-based aspect lexicon engine. It utilizes a pre-compiled valence dictionary mapping words to sentiment scores (+2.0 for "exceptional", -2.0 for "filthy"). During review ingestion, the text is tokenized into sentences. The analyzer detects intensifiers like "extremely" (amplifying valence by 1.5x) and negators like "not" or "never" (inverting the valence sign). It maps sentiment tokens to four hospitality aspects—Cleanliness, Service, Location, and Value—by matching domain taxonomy keywords. The final aspect rating blends sentence valence with user star ratings: sentenceAvg * 0.6 + starRating * 0.4, clamped to [1.0, 5.0]. This achieves sub-millisecond sentiment analysis with zero Python/PyTorch dependencies.
Q9 How did you verify system reliability across all features without manual testing?
Model Answer: We created a 4-tier automated opaque-box test runner in Node.js (testing/e2e/runner.mjs) executing genuine HTTP REST and SSE network calls against the running Spring Boot server on port 8081 with zero mocking. Tier 1 runs 170 feature isolation tests (5 tests across 34 distinct feature endpoints). Tier 2 runs 170 boundary, clamping, and negative input tests. Tier 3 executes 34 pairwise cross-feature interaction scenarios, and Tier 4 validates 6 multi-step end-to-end user workflows. In addition, we executed a 25-virtual-racer concurrency stress test and 14 headless browser scenarios with Playwright, achieving a 380/380 passing record certified by an independent test audit.
Q10 Why did you choose MongoDB over a traditional relational database like PostgreSQL?
Model Answer: In travel and hospitality platforms, search read performance and document containment are paramount. Using MongoDB's document model, user bookings are stored as embedded documents directly inside the users collection, eliminating expensive multi-table relational JOIN operations during dashboard itinerary queries and ensuring atomic updates during booking and cancellation. Furthermore, features like 3D spatial room configs (Room3dConfig) and polymorphic reviews (which attach interchangeably to either a Flight or a Hotel entity) require flexible nested schemas that would require complex junction tables or JSONB columns in SQL.
Q11 How do you manage security, CORS, and role-based access control (RBAC) in Spring Boot?
Model Answer: We implemented a multi-layered security model. In SecurityConfig.java, we defined a SecurityFilterChain bean with CORS wildcard permissions for Next.js and CSRF disabled for stateless REST. We restricted /api/reviews/moderation/** to hasAnyRole("ADMIN", "MODERATOR"). At the controller level, ReviewController.java inspects X-User-Role and Authorization bearer headers, explicitly throwing HTTP 403 Forbidden with a descriptive error message if a standard customer attempts to access the quarantine moderation queue. Passwords are encrypted using an injected BCryptPasswordEncoder bean.
Q12 What is the Cold-Start problem in recommendation systems, and how did MakeMyTour solve it?
Model Answer: The cold-start problem occurs when a brand-new user registers with zero historical booking or browsing data, rendering collaborative filtering algorithms ineffective. In RecommendationService.java, we solve this by implementing a curated baseline fallback catalog. On startup, the service clusters hotel records into thematic centroids (Beach, Heritage, Nature, Luxury) using keyword tokenization. When a user has no booking history, the engine serves top-rated properties from each centroid as a diverse exploratory set. As the user interacts—booking items or submitting upvotes/downvotes via RecommendationFeedback—the engine dynamically refines affinity weights, transitioning seamlessly from cold-start heuristics to personalized collaborative recommendations.
